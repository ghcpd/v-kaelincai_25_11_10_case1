Role
You are a software engineer responsible for implementing and testing the capabilities of AI models on the New feature subtype within the Feature & improvement category.
Your task is to provide two separate, complete Python projects (before / after) that implement a Search History Dropdown feature for an application search bar, exercise edge cases and optimizations, include automated tests, and run reproducibly with one command per project.
________________________________________
Title
Evaluation of Prime, Secondary, haiku, and gpt-5-mini on Feature & improvement — New Feature: Search History Dropdown
________________________________________
Description
This experiment evaluates AI models’ ability to design, implement and validate a small but UX-critical feature: a Search History Dropdown for an application search bar. The current search triggers only on Enter. The new feature must display the 5 most recent searches when the input is focused or as the user types, support click-to-repeat search, support keyboard navigation, persist history across sessions, and handle privacy/edge cases (clear history, opt-out). The goal is to deliver two projects:
• Project A — Pre-Feature (Baseline): search bar without history dropdown (Enter-only).
• Project B — Post-Feature (Enhanced): search bar with Search History Dropdown, keyboard navigation, persistence, privacy controls, and robust input handling.
Key evaluation criteria
• Correctness of feature behavior (display, selection, persistence).
• UX: keyboard & mouse interactions, accessibility (ARIA), responsiveness.
• Robustness: malformed inputs, non-string history items, large history, concurrency.
• Performance: minimal latency, efficient storage/lookup.
• Test coverage: unit and end-to-end tests, including edge cases.
• Reproducibility: environment scripts and one-command execution for full test runs.
• Quantitative metrics: correctness rate, keyboard navigation success, latency, persistence checks.

Requirements for the AI Model Output
1.	Test Scenario & Description
o	Describe the scenario and ability being tested: show and use the 5 most recent searches when the user focuses or types in the search field; clicking a history item triggers the same search; Up/Down + Enter navigates/selects items; Esc closes dropdown.
o	Specify expected input/output formats for automated tests (JSON or Python dict). Example: {"action":"focus","expected_dropdown": true, "expected_items":["x","y","z"]}.
o	Acceptance criteria: dropdown appears on focus/typing, shows up to 5 recent entries in correct (most-recent-first) order, clicking or selecting with keyboard triggers the same search request payload, history persists across page reloads, and privacy controls (clear, opt-out) work.
2.	Test Data Generation
o	Produce at least 5 structured test cases saved as test_data.json, covering:
• Normal case — user with empty history, performs searches, dropdown shows entries.
• Repeated-search case — duplicate entries, ensure ordering and deduplication policy.
• Malformed inputs — history contains non-string entries, extremely long strings, or control characters.
• Persistence case — history persists across simulated reloads and sessions; opt-out disables persistence.
• Accessibility & keyboard case — keyboard navigation (Up/Down/Enter/Esc), screen-reader attributes.
o	Each case must include: test id, initial state, user actions, expected dropdown contents/state, and pass/fail rules.
3.	Reproducible Environment
o	Provide requirements.txt and setup.sh (or Dockerfile) to create a consistent environment. Include test runner dependencies (pytest, Playwright or Selenium) and any small local storage shim.
o	Document how to start the baseline (Project A) and enhanced (Project B) demo apps, how to configure persistence location (in-memory vs local file), and how to run tests.
4.	Test Code
o	Generate executable Python test code that:
a. Starts the demo app and a lightweight HTTP server if required.
b. Uses headless browser automation (Playwright/Selenium) to simulate focus, typing, clicks, keyboard navigation, and page reloads.
c. Captures outputs: DOM state, emitted search requests (payloads), local storage contents, and console logs.
d. Compares actual outputs to expected results from test_data.json.
e. Reports per-test pass/fail and computes metrics: correctness_rate, keyboard_navigation_success, persistence_success_rate, and latency for dropdown display.
o	Tests must be runnable via run_tests.sh and accept a repeat parameter for stability checks.
5.	Execution Scripts
o	Provide run_tests.sh in each project to set up the environment (venv or Docker), start the demo server, run all tests, collect artifacts (screenshots, logs, results JSON), and gracefully stop servers.
o	Provide root-level run_all.sh that runs Project A then Project B tests, aggregates results_pre.json and results_post.json, and generates compare_report.md. One command should run the full workflow end-to-end.
6.	Expected Output
o	For every test case produce reference outputs (example JSON): expected dropdown presence, expected item list and order, expected search payload on selection, expected storage contents after actions.
o	Generate results_pre.json and results_post.json with per-test assertions, pass/fail, measured latencies (time-to-dropdown), and persistence verification.
o	Produce compare_report.md summarizing: feature correctness delta, keyboard navigation success rates, persistence behavior, and any regressions or remaining issues.
7.	Documentation / Explanation
o	Provide README.md explaining how to set up environments, run individual project tests, run the full experiment, and locate artifacts.
o	For each test case explain what it validates and why it matters (usability, privacy, accessibility).
o	Highlight pitfalls and failure modes (race conditions writing history concurrently, injection/malicious history entries, storage quota limits, cross-origin storage issues).
o	State limitations of the test harness (headless vs real-device differences) and recommend rollout steps (feature flag, gradual exposure, telemetry to monitor real users).
