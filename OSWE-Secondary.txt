Description
This experiment evaluates AI models’ ability to design, implement and validate a small but UX-critical feature: a Search History Dropdown for an application search bar. The current search triggers only on Enter. The new feature must display the 5 most recent searches when the input is focused or as the user types, support click-to-repeat search, support keyboard navigation, persist history across sessions, and handle privacy/edge cases (clear history, opt-out). The goal is to deliver two projects:
• Project A — Pre-Feature (Baseline): search bar without history dropdown (Enter-only).
• Project B — Post-Feature (Enhanced): search bar with Search History Dropdown, keyboard navigation, persistence, privacy controls, and robust input handling.
Key evaluation criteria
• Correctness of feature behavior (display, selection, persistence).
• UX: keyboard & mouse interactions, accessibility (ARIA), responsiveness.
• Robustness: malformed inputs, non-string history items, large history, concurrency.
• Performance: minimal latency, efficient storage/lookup.
• Test coverage: unit and end-to-end tests, including edge cases.
• Reproducibility: environment scripts and one-command execution for full test runs.
• Quantitative metrics: correctness rate, keyboard navigation success, latency, persistence checks.

Design choices and short justification
- LocalStorage for persistence: safe/sufficient for single-origin client-only demo; tests assert key presence; the opt-out checkbox toggles `search_history_opt_out` preventing writes.
- Deduplication policy: on save, the item moves to the front and duplicates removed — this is intuitive and prioritizes recency (used in tests).
- UI: Shows up to 5 recent items — quick to scan and is what the tests check for.
- Accessibility: ARIA attributes `role=listbox` and `role=option` plus `aria-selected` set when navigating items. Tests verify `aria-selected` in keyboard nav test.
- Performance: dropdown filtered with case-insensitive includes on typed input. We keep the in-memory list and only show up to 5 items to keep latency negligible in the demo.
- Robustness: code filters out non-string history entries, handles parse exceptions, caps the saved history to 100 items. Tests verify malformed inputs don’t crash.

Automated test limitations and caveats (one small list)
- Headless environment vs real device: headless semantics can differ (some key events or focus differences); manual QA with a real device/browser is recommended for final release.
- LocalStorage is per-origin; tests simulate reload but do not test cross-tab race conditions.
- Playwright version differences may require `playwright install` after environment setup.
- Large-scale usage may require server-based history storage & robust back-end checks; the demo covers client behavior.
